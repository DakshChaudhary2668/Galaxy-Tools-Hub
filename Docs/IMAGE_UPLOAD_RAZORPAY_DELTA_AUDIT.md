# Galaxy Tools Hub — Image Upload and Razorpay Delta Audit

**Audit date:** 2026-09-16
**Scope:** Targeted, read-only delta audit after Production Readiness Sprint 1
**Repository:** Galaxy Tools Hub monorepo
**Decision constraint:** Razorpay is the authoritative production payment architecture. A manual UTR flow is not recommended.

## 1. Executive Summary

The product image data model and storefront rendering are already capable of representing multiple images, but the admin workflow is still URL-only. There is no active file picker, browser upload helper, drag/drop component, progress state, or storage-aware replacement/removal workflow. The existing signed-upload endpoint is a useful foundation, but it is generic, accepts a client-selected bucket and path, includes `STAFF`, performs no file metadata validation, and returns no upload token for the normal Supabase `uploadToSignedUrl` client flow.

Supabase Storage is not provisioned. A live read-only check confirmed **zero buckets**. The minimum production architecture is one public `product-images` bucket, public reads, server-authorized per-object signed uploads, server-authorized deletes, a 5 MB bucket limit, and JPEG/PNG/WebP-only MIME restrictions. The browser must never receive the service-role key. Object paths should be generated by the server as `products/{productId}/{uuid}.{extension}` and never supplied verbatim by the client.

For MVP, support **exactly one primary product image**. The schema and product detail page can support a gallery, but the current admin/product-card experience is primary-image oriented. Multi-image management should be deferred.

The Razorpay integration is intentional but **partially implemented and not production-safe**. The earlier meaning of GTH-P0-005 (“UTR flow missing”) is incorrect. The actual P0 is that checkout trusts client-provided prices, the internal order is not bound to the Razorpay order, verification can be replayed or applied to a different internal order, and the confirmed amount/currency/capture status is not checked. A second P0 exists because successful payment finalization is neither inventory-gated nor atomic/idempotent; the live database has 5 products but only 1 inventory row.

`payment_verifications` is not used by active application code. A live read-only count returned 0 rows; `payments` also returned 0 rows. It is legacy/dead schema for the current Razorpay architecture. Do not build a UTR workflow around it.

The four planned Sprint 2 findings remain confirmed. No fixed Sprint 1 finding was reopened.

## 2. Current Product Image Architecture

### 2.1 Admin entry points

- Create: `apps/web/src/app/admin/(dashboard)/products/new/page.tsx`
  - Holds an `imageUrl` string state.
  - Renders a **Primary Image URL** text input and a browser `<img>` preview.
  - Sends `image_url: imageUrl.trim() || undefined` in the create payload.
- Edit: `apps/web/src/app/admin/(dashboard)/products/[id]/edit/page.tsx`
  - Loads the first `p.images[0].image_url` into the same string state.
  - Renders the same URL input/preview pattern.
  - Sends `image_url: imageUrl.trim() || undefined` in the update payload.
- There is no shared product form component; create and edit duplicate the image-field behavior.
- Repository-wide inspection found no active product file input, `FileReader`, object-URL preview, drag/drop handler, storage upload call, or upload-progress implementation. The previously tracked `apps/web/src/services/storage.service.ts` is deleted in the current working tree and there is no active replacement.

### 2.2 Frontend contract

`apps/web/src/services/product.service.ts` sends product create/update bodies as JSON with an optional `image_url`. `apps/web/src/services/api.ts` is a JSON API helper (`Content-Type: application/json`), not a binary/multipart uploader. The browser Supabase client in `apps/web/src/lib/supabase.ts` uses only the public Supabase URL and anonymous key; that is correct. The service-role key exists only in the server client in `apps/server/src/config/supabase.ts`.

Create and edit therefore use the same effective image contract: one optional URL string. Clearing the edit field produces `undefined`, so it does not currently express “remove the existing image.”

### 2.3 Backend persistence

`apps/server/src/controllers/product.controller.ts` accepts `image_url`, `image`, `images`, and `product_images` compatibility shapes, takes the first usable value, and writes one `product_images` row. It currently writes the same string into both:

- `product_images.public_url`
- `product_images.storage_path`

That works for existing static or remote URLs but does not preserve the intended distinction between a Storage object key and a public URL. Image insert/select/update results are not consistently checked for Supabase errors. Update changes only the first image row or inserts one when none exists.

The dedicated admin image endpoints in `apps/server/src/routes/product.routes.ts` and `apps/server/src/controllers/product.controller.ts` create/delete only `product_images` metadata. They do not upload or delete Storage objects.

### 2.4 Schema and multiple-image capability

`Docs/schema.sql` and `packages/types/index.ts` define `product_images` with:

- `product_id`
- required `storage_path`
- nullable `public_url`
- `is_primary`
- `sort_order`
- optional `alt_text`

The schema supports multiple rows per product, and the product detail client can render up to four image URLs as a gallery. The admin UI and ProductCard, however, primarily operate on one image. There is no database constraint ensuring only one primary image per product.

### 2.5 Storefront resolution

- Product list responses normalize each joined image to `public_url || image_url || storage_path`, prefer `is_primary`, then fall back to the first image.
- Product detail responses perform the same normalization.
- `apps/web/src/components/ProductCard/ProductCard.tsx` resolves `product.image`, then top-level `image_url`, then `images[0].image_url`, then `/images/placeholder.jpg`.
- `apps/web/src/app/product/[id]/ProductDetailClient.tsx` uses the first image as the main image and can render up to four thumbnails.
- `apps/web/next.config.js` permits HTTPS images from `*.supabase.co` and uses unoptimized Next images, so public Supabase Storage URLs are compatible without a new host rule.

Existing URL-backed rows must remain readable. New uploaded rows should store a true object path in `storage_path` and its public URL in `public_url`.

## 3. Existing Storage Infrastructure

The current implementation consists of:

- Bucket-name constants in `packages/constants/index.ts`, including `product-images`, `product-documents`, `brand-logos`, `payment-proofs`, and `invoices`.
- `POST /storage/signed-url` in `apps/server/src/routes/storage.routes.ts`.
- `adminAuthGuard` plus `OWNER`, `MANAGER`, or `STAFF` authorization.
- `SignedUrlRequestSchema` in `packages/types/index.ts`, which validates an allow-listed bucket and a relative path. It rejects leading slashes, backslashes, control characters, empty segments, `.` and `..` segments, and overlong paths.
- `apps/server/src/repositories/storage.repository.ts`, which uses the server-side service-role client to call `createSignedUploadUrl(path)`.

The endpoint is authenticated after Sprint 1 and ordinary customers cannot pass `adminAuthGuard`. That fixed finding remains fixed.

Current limitations:

- Bucket and full object path are selected by the caller.
- The route grants access to `STAFF`, while product mutations are limited to `OWNER` and `MANAGER`.
- No product ID/prefix ownership rule is enforced.
- No MIME type, extension, or file-size metadata is accepted or validated.
- Collision/upsert behavior is not explicitly fixed by the contract.
- The repository returns `signedUrl` and `path` only. It drops the token normally consumed by Supabase `uploadToSignedUrl`, and there is no browser uploader that uses either form.
- No `getPublicUrl` integration exists.
- No storage delete/replace integration exists.
- The live project has zero buckets, so positive URL generation cannot succeed yet.

## 4. Supabase Storage Gaps

| Area | Current state | Required state |
|---|---|---|
| Bucket | Zero buckets | Public `product-images` bucket |
| Bucket selection | Client selects any allow-listed bucket | Product-image endpoint fixes the bucket server-side |
| Object path | Client submits path | Server derives `products/{productId}/{uuid}.{ext}` |
| File types | No app validation; no bucket exists | JPEG, PNG, WebP only; reject SVG, GIF, HTML, and executable content |
| File size | No app validation; no bucket exists | 5 MB maximum in client, server request validation, and bucket config |
| Upload authorization | OWNER/MANAGER/STAFF generic signed URL | OWNER/MANAGER product-specific signed URL |
| Public URL | Not generated | Server returns/stores `getPublicUrl` result after successful upload |
| Collision behavior | Implicit | UUID object name, `upsert: false` |
| Replace/remove | Metadata-only endpoints | Server-coordinated metadata and Storage cleanup |
| Orphans | Not handled | Compensating delete and logged retry/reconciliation |

Supabase guidance relevant to this design:

- Storage writes are denied by default without RLS policies unless a trusted server/service role or signed-upload token authorizes them.
- A public bucket makes object reads public; write/delete operations remain controlled.
- Bucket-level file-size and MIME restrictions should be configured as defense in depth.
- Unique paths are preferable to overwrite because overwriting can serve stale CDN content.
- The service-role key bypasses RLS and must remain server-only.

References: [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), [bucket fundamentals](https://supabase.com/docs/guides/storage/buckets/fundamentals), [standard uploads](https://supabase.com/docs/guides/storage/uploads/standard-uploads), and [serving files](https://supabase.com/docs/guides/storage/serving/downloads).

## 5. Recommended Admin Image Upload Architecture

Use a product-specific, signed direct-upload flow rather than exposing the generic bucket/path endpoint to the product form.

### Create product

1. Admin selects one image locally; the browser validates type/size and renders a local preview.
2. Admin submits the product metadata **without** an image URL so the server can create the product and return its ID.
3. Browser requests an upload authorization for that product, sending only the product ID plus normalized file extension, MIME type, and size.
4. Server verifies `OWNER`/`MANAGER`, verifies the product exists, fixes bucket=`product-images`, derives `products/{productId}/{uuid}.{ext}`, and returns the signed-upload material needed by the client.
5. Browser uploads directly to Supabase Storage and reports progress/error.
6. Browser calls a product-image completion endpoint. The server persists `storage_path`, derived `public_url`, `is_primary=true`, and `sort_order=0`.
7. If upload succeeds but metadata persistence fails, the server performs a best-effort delete of the newly uploaded object and records the cleanup failure if deletion also fails.

This ordering can leave a newly created product without an image if upload fails, but it avoids uploading to a fake/pre-creation product path. The admin screen should keep the product open and offer **Retry upload**. That is the smallest safe design without distributed transactions.

### Edit product

1. Keep the current image until a replacement is fully uploaded and its metadata is saved.
2. Upload the new image to a unique path.
3. In one server-controlled metadata operation, make the new row primary and the old row non-primary/delete it.
4. Only after database success, delete the old Storage object when it is a managed `product-images` path.
5. If database persistence fails, best-effort delete the new object; do not remove the working old image.
6. If old-object deletion fails, keep the new image active and log/queue cleanup. Do not roll back the valid new image.

### Compatibility

Do not attempt to delete legacy values that are full external/static URLs. Cleanup must act only on validated object paths belonging to the `product-images` bucket. Existing `public_url`/`storage_path` fallback behavior should remain during migration.

## 6. Recommended Admin UX

MVP should support **one primary product image**.

Required controls and states:

- File picker labelled **Upload Product Image**.
- Local preview before save/upload.
- Accepted types shown as JPEG, PNG, WebP.
- 5 MB maximum shown beside the picker.
- Immediate client validation for MIME, extension, and size, repeated server-side and enforced by bucket config.
- Upload progress percentage or determinate progress bar.
- Explicit uploading, success, and error states.
- Retry after upload failure.
- Replace image on edit while preserving the old image until success.
- Remove image with confirmation on edit.
- Disable duplicate submit while product creation/upload is active.
- Preserve the rest of the product form if upload fails.

Drag/drop is optional and should be added only as a thin enhancement over the native file input. A media manager/library is unnecessary. Multiple gallery upload, sorting, and primary-image selection should be deferred because they add lifecycle and ordering complexity not required by the present ProductCard/admin experience.

## 7. Image Lifecycle / Cleanup Strategy

### Create succeeds

Persist a single primary `product_images` row after the upload completes. Store:

- `storage_path = products/{productId}/{uuid}.{ext}`
- `public_url =` the server-derived public URL for that bucket/path
- `is_primary = true`
- `sort_order = 0`

### Upload succeeds, product/image persistence fails

Because the recommended sequence creates the product before upload, the likely failure is image metadata persistence rather than product creation. Best-effort delete the newly uploaded object. If cleanup fails, emit structured server logs with bucket/path/product ID and retry later. A periodic orphan reconciler is a later hardening item, not required for MVP.

### Replacement

Always use a new UUID path and `upsert: false`. Commit the new image metadata before deleting the old object. This prevents broken product images and avoids CDN staleness associated with overwriting the same path.

### Removal

Use a server endpoint that resolves the image row, verifies it belongs to the target product, deletes/updates metadata, and then deletes the managed Storage object. A failed object deletion should be logged for retry. Legacy external URLs should have metadata removed without attempting remote deletion.

### Product deletion

Current hard delete relies on the `product_images.product_id ... ON DELETE CASCADE` relationship, which removes metadata but not Storage objects. Soft archive retains both metadata and images and should continue to do so. Before a hard delete, the server must collect managed object paths; after the database delete succeeds, it should best-effort delete those objects. The current controller does not do this.

## 8. Security Findings

### Controls that are correct

- The signed-upload endpoint is authenticated with `adminAuthGuard`.
- A normal customer cannot request a signed upload URL through that route.
- The browser Supabase client uses the anonymous key, not the service-role key.
- The current path schema rejects common traversal forms.
- Next.js only needs public HTTPS object delivery; no credential is embedded in image URLs.

### Controls still required

- Restrict product-image signing to `OWNER` and `MANAGER` to match product mutation rights.
- Remove caller control over bucket and full path.
- Verify the requested product exists before signing.
- Bind the signed path to `products/{productId}/` and a server-generated UUID.
- Validate extension, declared MIME, and size; enforce MIME/size again at bucket level.
- Reject SVG for MVP because it can carry active content; also reject GIF and all non-JPEG/PNG/WebP content.
- Use `upsert: false`; never let the client overwrite an arbitrary existing object.
- Keep deletes server-authorized and verify product/image ownership before deletion.
- Do not create broad anonymous/authenticated INSERT, UPDATE, or DELETE policies merely because the bucket is public.

The generic signed endpoint is broader than the new product-upload requirement and can mint upload capability for `payment-proofs` and `invoices`. Since signing uses the service-role client, this authorization boundary must be narrowed before any bucket is provisioned for browser upload.

## 10. Required Supabase Infrastructure

### Bucket

- **Name:** `product-images`
- **Visibility:** public
- **Maximum object size:** 5 MB
- **Allowed MIME types:** `image/jpeg`, `image/png`, `image/webp`
- **Path convention:** `products/{productId}/{uuid}.{jpg|jpeg|png|webp}`
- **Overwrite:** disabled (`upsert: false`)

A public bucket is appropriate for catalog imagery because these images are intentionally visible to every storefront visitor and benefit from stable CDN-backed URLs. Public does not mean public write.

### Policies and authorization

- **Read:** use the bucket's public-read behavior for object delivery. A separate broad `storage.objects` SELECT policy is not required for public URLs.
- **Upload:** no broad anonymous/authenticated INSERT policy. The browser uploads only with a short-lived, single-object signed token minted by the authenticated server endpoint.
- **Update:** no client update policy; unique-path replacement makes update unnecessary.
- **Delete:** no client delete policy; the authenticated server deletes only validated managed paths with the service-role client.
- **Server authorization:** OWNER/MANAGER only; server fixes the bucket and path prefix and verifies the product/image relationship.

### Database work

- Add a partial unique index to enforce at most one primary image per product, for example uniqueness on `product_id` where `is_primary = true`.
- Do not replace the existing columns. Preserve `public_url`, `storage_path`, `is_primary`, and `sort_order`.
- Apply changes through a versioned migration, not by editing production manually.

### Environment variables

No new browser secret is required. Continue using:

- Server only: `SUPABASE_SERVICE_ROLE_KEY`
- Server/browser public configuration: existing Supabase URL and anonymous/public key variables

Never add a `NEXT_PUBLIC_*` service-role variable. The bucket name can remain a checked-in constant because it is not secret; it does not need to become environment-driven unless environments deliberately use different names.

## 11. Razorpay Architecture Reassessment

### Current flow

1. Checkout sends products, product names, prices, quantities, contact, and shipping data from the browser.
2. `createCheckout` creates a pending internal order and related rows, then creates a Razorpay order.
3. The browser opens Razorpay Checkout with the returned public key ID and Razorpay order ID.
4. The success callback sends Razorpay order/payment/signature values plus an internal `orderId` to `/payments/verify`.
5. The server validates the HMAC and inserts a paid payment row, then decrements inventory and marks the order paid.

### Assessment

- **Implementation state:** partial.
- **Production-safe:** no.
- **Public key handling:** correct; returning `RAZORPAY_KEY_ID` is expected.
- **Secret handling:** the secret remains server-side; local absence alone would not be a P0.

Production blockers:

1. The “server-side calculation” still multiplies client-supplied `item.price`; it does not fetch authoritative product prices from the database.
2. The Razorpay order ID is not persisted against the internal order. The comment says it is stored, but the subsequent update stores only status fields.
3. Verification computes a valid Razorpay HMAC but trusts a separately supplied internal `orderId`. A valid payment/signature pair can therefore be presented with another internal order ID.
4. Verification does not fetch/confirm Razorpay payment `order_id`, amount, currency, status, or capture state against the internal order.
5. There is no idempotency guard. Repeated verification can insert multiple payment rows and decrement inventory repeatedly.
6. Payment rows record `amount: 0`, and neither `transaction_id` nor `gateway_reference` is unique.
7. Failed signature handling can mark the separately supplied internal order failed.
8. Order-item, address, order-status, and payment inserts/updates often ignore Supabase `{ error }` results.
9. There is no Razorpay webhook or reconciliation path for callback loss, asynchronous capture, retries, refunds, or disputes.
10. Payment success and inventory/order mutation are not atomic. Inventory is not reserved before payment.
11. The live database has 5 products and only 1 inventory row. Four products can therefore reach payment without a valid inventory contract and fail after money is captured.
12. Checkout assigns every order to one hard-coded guest profile UUID.
13. `GET /payments/order-status/:id` is unauthenticated and returns customer notes, a full address, phone data, and line items to anyone holding the order UUID.

### Minimum production completion

- Fetch product records/prices server-side and reject inactive/missing products and invalid quantities.
- Ensure every sellable product has inventory, validate/reserve before creating the Razorpay order, and define reservation expiry/release.
- Persist a pending `payments` row containing the true amount and the Razorpay order ID as `gateway_reference`.
- Add database uniqueness for `gateway_reference` and non-null `transaction_id`.
- Resolve the internal order from the stored Razorpay mapping during verification; never let the client select the order to mark paid.
- Verify signature with a timing-safe comparison and fetch the Razorpay payment/order to validate binding, amount, currency, status, and capture.
- Make fulfillment finalization idempotent and transactional at the database boundary.
- Add a signed Razorpay webhook and idempotent event processing/reconciliation.
- Check every database error and return recoverable, non-contradictory states.
- Require Razorpay credentials and a webhook secret in production deployment validation without printing them.
- Replace the shared guest UUID with a real authenticated customer or a deliberate guest-order identity/access-token design.

## 12. Corrected GTH-P0-005 Status

**Status: CONFIRMED, MEANING CORRECTED**

**Correct title:** **GTH-P0-005 — Razorpay payment amount and order binding are not authoritative or replay-safe**

**Evidence:** `apps/server/src/controllers/payment.controller.ts` trusts client prices, does not store the Razorpay-order/internal-order mapping, accepts a client-selected internal `orderId` during verification, does not verify the captured amount/currency/status, records amount zero, and has no idempotency constraint or webhook reconciliation.

**Impact:** A checkout can be created from tampered prices; a valid Razorpay payment response can be applied to the wrong internal order; repeated verification can repeat side effects; and the database can report paid state without authoritative payment facts.

**Required correction:** authoritative server pricing, persistent Razorpay/internal-order mapping, amount/currency/capture verification, unique/idempotent payment processing, transactional order finalization, and webhook-backed reconciliation.

GTH-P0-005 is **not** “UTR flow missing.” Missing local development credentials alone are not the reason for P0 classification.

## 15. NEW Findings

### GTH-P0-006 — Paid-order finalization is not inventory-safe, atomic, or idempotent

- **Severity:** P0
- **Exact files:** `apps/server/src/controllers/payment.controller.ts`; `apps/server/src/services/order.service.ts`; `apps/server/src/services/inventory.service.ts`; `Docs/schema.sql`
- **Evidence:** Verification inserts a paid payment before calling `markPaid`. `markPaid` loops through inventory decrements and then updates the order, with no transaction or prior paid/idempotency check. Checkout does not reserve inventory. A live read-only check found 5 products but only 1 inventory row.
- **Root cause:** Payment confirmation, inventory mutation, and order transition are separate application-level operations without a single idempotent database boundary or a complete inventory prerequisite.
- **Recommended fix:** Complete the controlled inventory backfill first; validate/reserve inventory before Razorpay order creation; finalize the payment/order/inventory transition through an idempotent transactional database operation keyed by the unique gateway payment/order reference; make retries return the prior result without repeating stock movement.
- **Complexity:** High (cross-cutting payment, inventory, database migration/RPC, and failure-recovery work).

### GTH-P1-011 — Admin product image upload is absent and the signed-upload contract is incomplete

- **Severity:** P1
- **Exact files:** `apps/web/src/app/admin/(dashboard)/products/new/page.tsx`; `apps/web/src/app/admin/(dashboard)/products/[id]/edit/page.tsx`; `apps/web/src/services/product.service.ts`; `apps/web/src/services/api.ts`; `apps/server/src/repositories/storage.repository.ts`
- **Evidence:** Both forms accept only a URL string. No active upload component/service exists. The API helper is JSON-only. The signed-URL repository returns URL/path but drops the token normally used by `uploadToSignedUrl`; there is no frontend consumer.
- **Root cause:** Image persistence was implemented as URL compatibility plumbing, while the file-upload workflow was never connected end to end.
- **Recommended fix:** Implement the one-primary-image direct signed-upload flow in Sections 5–6, including a reusable picker/preview/progress component and a complete signed-upload response contract.
- **Complexity:** Medium.

### GTH-P1-012 — Signed upload authorization and object scope are too broad

- **Severity:** P1
- **Exact files:** `apps/server/src/routes/storage.routes.ts`; `apps/server/src/controllers/storage.controller.ts`; `apps/server/src/repositories/storage.repository.ts`; `packages/types/index.ts`; `packages/constants/index.ts`
- **Evidence:** Any OWNER, MANAGER, or STAFF caller can select any allow-listed bucket and relative path, including invoice/payment-proof namespaces. The request contains no product binding, MIME, extension, or size. Path traversal is restricted, but namespace authorization is not.
- **Root cause:** A generic storage utility endpoint is being treated as the authorization boundary for multiple business domains.
- **Recommended fix:** Add a product-specific OWNER/MANAGER signing contract; fix the bucket server-side; derive the path server-side from a verified product ID; enforce 5 MB and JPEG/PNG/WebP; reject SVG/executables; use UUID paths and `upsert: false`. Keep unrelated bucket operations behind their own domain authorization.
- **Complexity:** Medium.

- **Severity:** P1
- **Exact files:** `apps/server/src/controllers/product.controller.ts`; `apps/server/src/routes/product.routes.ts`; `apps/server/src/repositories/storage.repository.ts`; `Docs/schema.sql`
- **Evidence:** URL strings are duplicated into `public_url` and `storage_path`; image insert/select/update errors are not consistently checked; clearing edit does not remove; metadata delete does not delete Storage; hard product delete cascades metadata only; replacement does not clean an old object.
- **Root cause:** Product image metadata and Storage object lifecycle are independent, with no managed-path distinction or compensating cleanup.
- **Recommended fix:** Store path and URL separately, check every database result, add server-controlled completion/replace/remove operations, delete only validated managed paths, and use best-effort compensating cleanup with structured logging.
- **Complexity:** Medium–high.

### GTH-P1-014 — Public order-status lookup exposes customer/order details without access proof

- **Severity:** P1
- **Exact files:** `apps/server/src/routes/payment.routes.ts`; `apps/server/src/controllers/payment.controller.ts`
- **Evidence:** `GET /payments/order-status/:id` has no authentication or order-specific token and returns customer notes, full shipping address/phone fields, amounts, and line items for the supplied UUID.
- **Root cause:** Possession of an internal database UUID is treated as sufficient authorization for a response containing personal/order data.
- **Recommended fix:** Require the authenticated order owner or a separate high-entropy, revocable guest lookup token; minimize the public response; never expose internal IDs as the sole access control.
- **Complexity:** Medium.

### GTH-P2-006 — Product image gallery endpoint has schema drift

- **Severity:** P2
- **Exact files:** `apps/server/src/controllers/product.controller.ts`; `apps/server/src/routes/product.routes.ts`; `Docs/schema.sql`
- **Evidence:** `getProductImages` queries `product_variants` and may filter `product_images.variant_id`, but the audited schema defines neither that table relationship nor a `variant_id` column on `product_images`. No active frontend caller was found.
- **Root cause:** Variant-aware gallery logic was added without a matching active schema/contract and is currently dormant.
- **Recommended fix:** For MVP, simplify the endpoint to product-level images only. Reintroduce variant images later only with a deliberate schema migration and consumer contract.
- **Complexity:** Low.
